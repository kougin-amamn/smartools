# Smartools — デザインコンセプト

[サービスコンセプト](./service-concept.md)(使いやすさを、美しく。)を、見た目と操作に落とした考え方です。数値と書き方は [ui.md](./ui.md) と [design/m3-expressive.md](./design/m3-expressive.md) に書きます。

## 1. デザイン哲学

**Functional Beauty — 機能美**

Smartoolsでは、使いやすさを追求した結果として生まれる美しさを重視します。

装飾そのものを否定するのではなく、視覚表現に目的を持たせます。例えば、ストップウォッチの円形ゲージは、時間の経過を直感的に把握するために使用します。一方、情報理解や操作に寄与しないアニメーションは原則として採用しません。

### 1.1 デザイン原則

1. 機能優先 — 視覚表現は機能の理解と操作を支援する。
2. 明快さ — 何ができるか、何が起きているかを分かりやすくする。
3. 一貫性 — 共通する操作や状態には共通の表現を使う。
4. 適応性 — 画面サイズや入力方法の違いに自然に対応する。
5. 節度 — 色、動き、装飾を目的に応じて必要な範囲で使う。

### 1.2 デザイン判断の優先順位

デザイン上の要素が競合する場合、原則として次の順序で判断します。

1. 正確性・安全性
2. アクセシビリティ
3. 操作性・分かりやすさ
4. 情報の視認性
5. サービス全体の一貫性
6. 視覚的な美しさ・演出

ただし、個別ツールの目的や利用状況に応じて調整します。

## 2. デザイン言語: Material 3 Expressive

デザイン言語は Google の [Material 3 Expressive](https://design.google/library/expressive-material-design-google-research)(M3E)に沿います(2026-11-15)。

M3E は、色・形・大きさ・動き・まとまり(容器)で大事な操作を目立たせ、関係する物をまとめる考え方です。研究では、大事な部品を見つける速さが上がり、年齢による差も小さくなりました。機能美(1章)と同じ向きなので、次のように受け止めます。

| M3E の考え | Smartools での受け止め方 |
| --- | --- |
| 大事な操作を大きく・目立たせる | 主な操作は大きさ・色・形で一目で分かるようにする(機能優先・明快さ) |
| 関係する物を容器やまとまりでくくる | 関連する操作は、まとまり(ボタンのまとまり・カード)にする(情報設計) |
| 色と形で表情を付ける | M3 の色の役割と形の段階だけを使い、ツールごとに作らない(一貫性) |
| ばねの動きで手応えを返す | 動きは操作の手応えと状態の変化にだけ使う(節度) |
| 表現の強さは場面で選ぶ | Smartools は中くらい。道具のサイトなので、落ち着いた見た目を好む人にも合わせる |

M3E の中でも、次の物は採りません。

- 決まった形を崩す並べ方(研究で使いやすさが下がった)。
- 文字のラベルを消して絵だけにすること。
- 押した時に角が四角くなる動き(見た目が良くないため。2026-11-15)。
- フォントの読み込み(端末の文字を使い、通信を増やさない)。

## 3. ビジュアルデザイン

### 3.1 基本方針

- 平らな面と容器(カード・シート)を基本とし、影は控えめにする。
- 情報と操作の階層を、大きさ・色・容器で明確にする。
- 適切な余白によって視認性を高める。
- 角の丸さは M3 の段階だけを使い、部品の役割で使い分ける。
- 装飾だけの立体表現や過剰なアニメーションを避ける。
- 操作部品の形状・状態・配置に一貫性を持たせる。

### 3.2 カラー

Material 3 の標準の色の組(基準の紫 `#6750A4` から作られた、主・第二・第三・面・容器・輪郭・エラーの役割)を使います(2026-11-15。それまでの配色の検討は [log.md](./log.md))。

- 色は役割の名前(トークン)で書き、ツールごとの色を作らない。
- 複数のカラーテーマを提供する(テーマの色から役割の色を作る。見直し中)。
- ライト・ダーク表示に対応する。
- 色の意味をツール間で統一する(主・もう一方の状態・エラー)。
- コントラストと可読性を確保する(ふつうの文字 4.5 以上)。

### 3.3 形と大きさ

- ボタンは まるい形、カードは `--shape-large`、シートは `--shape-extra-large` を基本にする。
- 主な操作は大きくする(高さ 56px 以上、いちばん大事な1つは 96px くらい)。
- 押す所は 44px 以上を確保する。

### 3.4 アニメーション

アニメーションは、次の目的がある場合に採用します。

- 状態の変化を伝える。
- 時間や進捗を表現する。
- 操作に対するフィードバックを提供する。
- 情報の関係性を理解しやすくする。

押した時の手応えは、全ページ共通の波紋(M3 の ripple)にそろえ、ツールごとに作りません。位置や大きさの変化には M3E のばねの動き(少し行き過ぎて戻る)を使います。装飾だけを目的とする動きは原則として避け、動きを抑える設定では形と位置の動きを止めます。

## 4. UI・UX設計原則

### 情報設計

- 主要情報を最も分かりやすい位置に配置する。
- 関連する操作をまとめる。
- 必要性の低い情報は視覚的な優先度を下げる。

### 操作設計

- 主要操作を明確にする。
- 操作可能・操作不可の状態を区別する。
- 操作結果を適切にフィードバックする。
- 押して文字が変わるボタンでも、大きさを変えない。
- 誤操作を防ぎ、必要に応じて回復手段を用意する。

### レスポンシブ設計

- スマートフォンを含む多様な画面サイズに対応する。
- 画面の向きによって必要なレイアウトを調整する。
- 画面サイズにかかわらず主要操作へアクセスできるようにする。
- ツールのページでは、ヘッダを隠して画面を広く使う(右上のつまみで出す)。

### アクセシビリティ

- 意味のあるHTML構造を使用する。
- キーボード操作とフォーカス表示に配慮する。
- 文字・色・操作領域の可読性を確保する。
- スクリーンリーダーなどの支援技術への対応を考慮する。

## 5. 例外と拡張

Smartoolsの標準デザインは、実用性と機能美を優先します。ただし、ツールの目的上、より豊かな視覚表現が必要な場合は例外を認めます。

### ランチャー

3D本棚・3D美術館などのランチャーは、ツールを探して開く入り口を楽しく見せる物として、例外とします(2026-11-14)。立体表現や演出を使ってかまいません。ただし、ふつうの一覧(フラットな表示)はいつでも選べるようにします。

### DJツール(移した)

DJツールは、機器を模した表現が操作体験の一部となるため例外としていましたが、2026-11-11〜12 に別コンセプトのサイト [Toolbox Pro](https://github.com/kougin-amamn/toolbox-pro) へ移しました。

例外を設ける場合でも、操作性・可読性・基本的なアクセシビリティは維持します。

## 6. AIによるデザイン設計

AIがSmartoolsの新規ツールを設計・改善する際は、[サービスコンセプト](./service-concept.md)とこの文書を上位の判断基準として扱います。

### 推奨プロセス

1. 目的の理解 — ツールの用途、利用者、利用場面を把握する。
2. 情報・操作の整理 — 主要機能、情報の優先順位、操作の流れを定義する。
3. UI設計 — この文書と既存UI規約([ui.md](./ui.md))に基づいて構成する。
4. 実装 — 共通コンポーネント(`common/`)と既存のテーマ機構を優先する。
5. 検証 — 機能・操作性・視認性・一貫性を確認する。
6. 改善 — 問題とその理由を記録し、必要な変更を行う。
